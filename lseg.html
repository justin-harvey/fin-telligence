Two servers, one auditable answer

lseg-mcp — resolves & drafts

The open-source field expert.

Resolves a concept (“gross profit”) to the correct modern TR.* field, validates it against LSEG's COA/FCC mapping matrix, and drafts the runnable lseg-data call. It never returns market data — it only gets the retrieval right.

Fin-Telligence — verifies & attests

The audit layer.

Runs the landed snapshot through guard → grounding → hash-chained audit, reconciles a reported figure against the components that should compose it, and refuses on any mismatch. The join point is ingestion, not runtime.

How this differs from standard financial AI

Most commercial text-to-SQL and financial-AI platforms prioritise helpfulness and flexibility, handing the user a best-guess answer. Fin-Telligence prioritises non-repudiation and hard refusal — the individual patterns are standard computer-science primitives, but combining them into a zero-tolerance ground-or-refuse pipeline with cryptographic attestation is the uncommon choice.
FeatureStandard financial AI / text-to-SQLFin-Telligence architecture
SQL safety System prompts (“only write SELECT”) or generic DB permissions Pre-execution AST parsing (guard.js) enforcing SELECT-only, CTE allow-lists, and forced LIMIT bounds
Field mapping The model guesses a field name from the prompt lseg-mcp resolves the concept to the correct TR.* code and validates it against the COA/FCC matrix before ingest
Numeric accuracy LLM-as-a-judge or prompt engineering to format DB rows Deterministic post-prose verification (grounding.js) that matches every number back to SQL row outputs
Failure mode Best-guess response with potential rounding or hallucination errors Explicit refusal. If a single number can't be mapped to the raw data, the response is destroyed
Audit logging Standard cloud event logs (CloudWatch / Datadog, SOC 2 trails) Cryptographic hash-chaining (audit.js) where altering a past prompt, query, or output breaks chain verification

From synthetic to live in one credential

The values here are synthetic, authored so the identities hold exactly. The ingest seam (src/lseg-ingest.js) is a session interface: FakeLsegSession runs the whole path with no entitlement (this demo), and RealLsegSession fetches real fundamentals through lseg-data. Set LSEG_APP_KEY (an entitled LSEG Data Platform / Workspace app key), pip install lseg-data, and fintel lseg ingest --live attests genuine LSEG data. Nothing downstream changes — the guard, grounding, and audit chain are identical.

Run it yourself

# synthetic — no LSEG entitlement needed
node bin/fintel.js lseg seed
node bin/fintel.js lseg fundamentals IBM.N FY2023   # attested snapshot, each concept → its TR.* field
node bin/fintel.js lseg reconcile IBM.N FY2023      # gross profit = revenue − cost of revenue
node bin/fintel.js lseg ingest IBM.N --period FY2024   # land data via the ingest seam (fake session)
node bin/fintel.js lseg audit                        # verify the LSEG audit chain

# real LSEG data — needs an entitlement
export LSEG_APP_KEY=<your-app-key> # and: pip install lseg-data, Workspace running
node bin/fintel.js lseg ingest IBM.N --period FY2023 --live

What is real, and what is synthetic

Real: the instrument RICs (IBM.N, AAPL.O, VOD.L) and the TR.* field codes — validated against LSEG's mapping matrix through lseg-mcp. Synthetic: every value in the fundamentals table, authored so the accounting identities hold exactly and labelled synthetic. For a tool about traceable figures, fabricated data labelled as fabricated is fine; fabricated data presented as real is the exact failure this project exists to prevent. Nothing here is investment advice or a claim about any company's actual results.
